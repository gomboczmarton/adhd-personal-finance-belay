# Step 1 Branching Moment — Three Data-Architecture Directions

Fable Flow Phase 3 applied to schemas: three *wildly different* ways to organize the
harness's persistent state. React; we converge and then define the concrete schemas.

**Lessons anchoring this (from the reference repo, semantics only):**
- The reference data layer converged to a hybrid — markdown envelope "packages" (human),
  JSON state/overrides (machine), and Python constants — and needs a dedicated proactive
  skill (`verify-budget`) solely to keep them in sync. **Sync drift is the enemy.**
- The wealth ledger exists as both `.json` and `.md` — evidence that both humans and
  scripts genuinely need access, and that dual-format duplication happens if the
  architecture doesn't decide who owns the truth.
- Monthly artifacts (opening, lookahead, allocation checklist, reconciliation) are
  naturally *generated documents*, while packages/overrides are *edited state*.

**Requirements every direction must satisfy:**
- `schema_version` on every file; migration story (D1, blindspot #3)
- journey-capable: partial/gradual strategy adoption, mode changes without data loss (D2a)
- deterministic scripts own all derived numbers (D4); no personal data in shipped
  examples (all samples below use the synthetic persona "Alex")

All directions share one hard rule: **exactly one owner per fact.** Anything readable in
two places is generated from the one owner by a script.

---

## Direction A — "File Cabinet": typed domain files

Machine-first. Small, typed YAML/JSON files per domain; months are folders; markdown
exists ONLY as generated reports, never as state.

```
finance/
  config/
    accounts.yaml        # accounts, cards, mapping configs (per-account ingestion)
    strategy.yaml        # mode journey: awareness|envelopes, per-category adoption
    categories.yaml      # canonical keys + display names (language via D6)
  knowledge/
    yearly-bank.yaml     # recurring annual items, due months
    merchant-map.yaml    # learned "what does this transaction mean"
  months/2026-07/
    transactions.csv     # normalized, deduped (generated by ingestion)
    budget.yaml          # allocations for the month (edited state)
    overrides.yaml       # month-specific adjustments
    reports/             # generated: reconciliation.md, snapshot.html, budget.xlsx
```

```yaml
# strategy.yaml (journey-capable)
schema_version: 1
mode: awareness                # starting point, not a lifetime setting
envelope_adoption:             # partial adoption per D2a
  groceries: {since: 2026-09, envelope: family}
```

- **Strengths:** dead-simple for scripts and evals; clean git diffs; conventional; each
  file small enough for the agent to read whole. Cheapest to build and migrate.
- **Weaknesses:** the human browses *reports*, not state — editing YAML is nobody's joy
  (ADHD-hostile if the user must touch it); the "one owner" rule lives on discipline.

## Direction B — "Ledger": append-only event log, derived views

Accountant's-soul architecture. One append-only `events.jsonl` is the *only* mutable
thing; every other file is a derived, rebuildable view.

```
finance/
  events.jsonl           # THE truth: one JSON event per line, append-only
  views/                 # ALL generated, rebuildable via `uv run rebuild.py`
    current-strategy.yaml, categories.yaml, months/2026-07/...
```

```jsonl
{"v":1,"ts":"2026-07-02","type":"txn.imported","account":"main","hash":"ab12...","amount":-14500,"desc":"LIDL BUDAPEST"}
{"v":1,"ts":"2026-07-02","type":"txn.categorized","hash":"ab12...","category":"groceries","by":"agent","confidence":0.93}
{"v":1,"ts":"2026-07-05","type":"strategy.adopted","scope":"groceries","strategy":"envelope","envelope":"family"}
{"v":1,"ts":"2026-07-05","type":"decision.logged","text":"tried envelope for groceries only"}
```

- **Strengths:** the D2a journey is *literally the data model* — every convergence step
  is an event; perfect audit trail ("why is this categorized so?"); dedup is natural
  (event hashes); time-travel for evals ("state as of March"); no sync drift by
  construction.
- **Weaknesses:** humans can't browse truth directly (only views); highest build cost
  (rebuild engine + event taxonomy up front); mistakes need compensating events, which
  is conceptually heavier for a non-programmer user; agent must never edit views.

## Direction C — "Notebook": markdown-native with structured frontmatter

Agent-native. State lives in human-readable markdown documents whose YAML frontmatter
(and fenced data blocks) is the machine-parsed part — one file is BOTH the human view
and the machine state, eliminating dual-format duplication the other way around.

```
finance/
  strategy.md            # prose + frontmatter: the user's journey, readable as a story
  accounts.md
  knowledge/yearly-bank.md, merchant-map.md
  months/2026-07/
    budget.md            # frontmatter: allocations; body: notes, agent explanations
    reconciliation.md    # generated, quiz-style readable
    transactions.csv     # the one non-md artifact (normalized data)
```

```markdown
---
schema_version: 1
mode: awareness
envelope_adoption: {groceries: {since: 2026-09, envelope: family}}
---
# My strategy
Started awareness-only in July. Groceries kept surprising me, so from September
the agent and I try one envelope for it. Next review: October.
```

- **Strengths:** the state itself reads like a shame-free journal — the most
  ADHD-friendly and demo-charming option; closest to how the reference repo *feels*
  (packages are markdown); the agent reads/writes its native format; frontmatter is
  still deterministic to parse.
- **Weaknesses:** users editing prose can break frontmatter (needs a validating hook);
  scripts must go through a frontmatter-parsing layer; large data (transactions) still
  needs CSV sidecars, so it's honestly md+CSV, not pure md.

## Comparison

| Criterion | A · File Cabinet | B · Ledger | C · Notebook |
|---|---|---|---|
| D2a journey support | good (strategy.yaml) | **native** (events ARE the journey) | good (+ human story) |
| Script determinism (D4) | **best** | best (after rebuild engine) | good (frontmatter layer) |
| ADHD/human readability of state | via reports only | via views only | **state itself readable** |
| Sync-drift risk (ref-repo lesson) | discipline-dependent | **zero by construction** | low (one file = both) |
| Git diff / audit quality | good | **perfect audit** | good |
| Eval-ability | easy | easy + time-travel | medium (parse layer) |
| User-breaks-it risk | low | lowest | **highest** (prose edits) |
| Build cost to first demo | **lowest** | highest | medium |
| Migration/versioning | per-file, easy | event-version, easy | per-file, easy |

**Hybrids are legal.** E.g. C's readable notebook files as edited state + B's event log
for transactions/categorization only (where audit and dedup matter most) is a plausible
convergence — react and we'll shape it.
